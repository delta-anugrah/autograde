### C3. Docker image tidak self-booting — HikrobotCamera hardcoded tanpa SDK ✅

**File:** `src/ripe_recognition/main.py:88`, `src/ripe_recognition/integrations/camera/hikrobot_camera.py:31`

`main.py` selalu menginstansiasi `HikrobotCamera()` tanpa kondisi atau env flag:
```python
camera = HikrobotCamera()  # selalu, tidak ada fallback
```

`hikrobot_camera.py.__init__` langsung `raise RuntimeError` kalau `_SDK_AVAILABLE = False`:
```python
if not _SDK_AVAILABLE:
    raise RuntimeError("MvImport SDK tidak ditemukan...")
```

`Dockerfile` tidak menginstall atau meng-copy Hikrobot MvImport SDK — hanya `libusb-1.0-0`.
Akibatnya: image Docker yang di-commit sekarang crash saat startup sebelum model bahkan dimuat.

Tidak ada `CAMERA_TYPE` env var atau fallback ke `OpenCVCamera` di production image.

**Fix:** tambah env var `CAMERA_TYPE` (default `hikrobot`, opsi `opencv`/`photo`)
di `main.py` startup, atau ship SDK di Dockerfile (lebih berat).

### C4. Blocking lock di async context — freeze event loop 5 detik ✅

**File:** `src/ripe_recognition/services/capture_service.py:29`

`capture_manual_reject` adalah sync function yang:
1. Acquire `threading.Lock`
2. Call `camera.grab_frame()` (HikrobotCamera timeout = 5000ms)

Dipanggil langsung dari async controller tanpa `run_in_executor`.
Setiap manual capture membekukan seluruh asyncio event loop selama up to 5 detik:
semua WebSocket, MJPEG stream, dan API call lain terhenti.

**Fix:** wrap call ke `capture_manual_reject` dalam `asyncio.get_event_loop().run_in_executor(None, ...)`

## 🟠 HIGH — behavior salah, data loss, race condition

### H1. `result_queue` shared oleh semua client `/api/video_feed` — bukan broadcast ✅

**File:** `src/ripe_recognition/services/streaming_service.py:16`, `src/ripe_recognition/core/dependencies.py`

`StreamingService` di-inject dengan `@lru_cache` — semua request ke `/api/video_feed` berbagi
satu instance yang sama dengan satu `result_queue` yang sama.

`generate_frames()` tiap client memanggil `result_queue.get()` langsung:
```python
frame_bytes = self.state.result_queue.get()
yield (b"--frame\r\n" ... + frame_bytes + b"\r\n")
```

Dengan 2 client terhubung, frame dibagi bergantian (client A dapat frame 1, client B dapat frame 2).
Bukan broadcast — masing-masing client hanya dapat setengah frame rate, dan framenya berbeda.

**Fix:** ganti model pull-from-queue menjadi model broadcast per-frame, misalnya:
- Simpan frame terakhir di `RuntimeState.latest_frame: bytes | None`
- Setiap generator membaca `latest_frame` dengan polling/asyncio Event

---

### H2. `event_queue.put()` blocking — bisa stall processing thread ✅

**File:** `src/ripe_recognition/workers/frame_processing_worker.py:230`, `src/ripe_recognition/services/capture_service.py:42`

Keduanya call `event_queue.put(event)` tanpa `block=False`.
`event_queue` punya `maxsize=10`. Kalau `EventBroadcastWorker` lambat (WebSocket client lemot),
queue penuh dan processing thread berhenti total — tidak ada deteksi selama itu.

**Fix:** pakai drop-old pattern yang sama seperti `result_queue`:
```python
try:
    self.state.event_queue.get_nowait()
except queue.Empty:
    pass
self.state.event_queue.put_nowait(event)
```

### H3. TP status tidak pernah sampai ke webhook atau WebSocket ✅

**File:** `src/ripe_recognition/workers/frame_processing_worker.py:215-229`

Payload event hardcode `"tp_status": None, "tp_score": 0` meskipun ada `_last_tp` yang di-pair.
TP disimpan ke file `_tp.json` dengan benar, tapi tidak pernah dikirim ke `palmgrade-api` atau WebSocket.
Dashboard tidak pernah tahu ada TP.

**Fix:** baca `_last_tp` sebelum reset dan sertakan di event dict dan webhook payload.

### H4. `machine_id` tidak ada di WebSocket event DAN webhook manual capture ✅

**File:** `src/ripe_recognition/services/capture_service.py:42-66`

Auto detection (`frame_processing_worker.py:210-223`) menyertakan `machine_id` di event dict dan webhook.
Manual capture (`capture_service.py`) tidak menyertakannya di dua tempat:

1. **Event queue** (`line 42-54`): event dict tidak punya field `machine_id` → WebSocket client tidak dapat routing info
2. **Webhook payload** (`line 56-66`): payload tidak punya `machine_id` → `palmgrade-api` tidak bisa route ke panel yang benar

Akibatnya: semua hasil manual capture hilang di dashboard karena FE tidak tahu dari line mana datangnya.

**Fix:** tambahkan `"machine_id": self.settings.machine_id` ke keduanya di `capture_service.py`.
Note: `CaptureService` perlu akses `Settings` — inject lewat constructor atau `Depends(get_settings)`.

### H5. `_save_tp` pakai `datetime.now()` bukan timestamp yang di-pass ✅

**File:** `src/ripe_recognition/workers/frame_processing_worker.py:90`

`_save_tp` menerima `timestamp` string (dari `_save_ripeness`) tapi memanggil `datetime.datetime.now()` lagi untuk `date_folder`.
Kalau deteksi terjadi tepat sebelum tengah malam:
- `_ripeness.json` masuk folder tanggal A
- `_tp.json` masuk folder tanggal B

`ResultRepository.list_today_results()` group file per date folder → TP dan ripeness tidak pernah di-merge.

**Fix:** parse `date_folder` dari `timestamp` parameter, bukan `datetime.now()`.

### H6. Track cleanup hapus `_processed_objects` — single-trigger bisa dilanggar ✅

**File:** `src/ripe_recognition/workers/frame_processing_worker.py:249-252`

Setelah 10 frame tidak aktif, cleanup loop menghapus `track_id` dari `_processed_objects`:
```python
self._processed_objects.discard(tid)
```

Root cause yang lebih tepat: bukan hanya soal ByteTrack "recycling" integer ID (yang memang bisa terjadi),
tapi juga bahwa dedup state hilang begitu track dianggap inactive. Buah yang sama yang sempat keluar
frame lalu masuk lagi (misalnya getaran kamera, atau buah terpantul) bisa mendapat track ID baru
atau melewati cooldown 10 frame, lalu ter-save ulang.

**Fix:** pertimbangkan untuk tidak hapus dari `_processed_objects`, atau gunakan
`(track_id, first_seen_frame_counter)` tuple sebagai key agar unik lintas object lifecycle.

### M2. Komentar middleware order menyesatkan (behavior aktual sudah benar) ~~DIBATALKAN~~

**File:** `src/ripe_recognition/main.py:47-61`

~~Temuan awal audit ini salah.~~

Starlette `add_middleware` memang pakai `insert(0, ...)`. Dengan urutan pemanggilan sekarang:
1. `add_middleware(LicenseGuardMiddleware)` → stack: `[License, Router]`
2. `add_middleware(CORSMiddleware)` → insert di index 0: `[CORS, License, Router]`

Urutan eksekusi: **request** masuk lewat CORS dulu → License → Router.
Urutan response: Router → License → **CORS** (response keluar lewat CORS terakhir).

Artinya 403 dari License **memang melewati CORS** sebelum sampai ke browser.
Behavior aktual sudah benar — browser bisa baca error message, tidak dapat CORS error.

Yang salah hanya **komentar kode** di `main.py:47`:
```python
# License Guard — wired before CORS so it runs outermost  ← SALAH, sebenarnya CORS yang outermost
```

**Fix:** perbaiki komentar saja, tidak perlu ganti urutan middleware.
